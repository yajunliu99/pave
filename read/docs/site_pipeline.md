# 任意路口的一键流程

入口：`scripts/pipeline/run_site_pipeline.py`。从一个路网节点出发，依次完成取图 → 候选区域描绘 → 分类 → 出口复核 →（可选）车道数核查 → 图集 → 信号标志 → 标注图 →（可选）街景车道对齐 → 导出到 `results/` → 更新 dashboard（单文件 `dashboard/intersection_explorer.html`，只重新处理本路口）。代码里不含任何具体路口的路径、编号、方位或日期；路口特有的输入只出现在该路口的配置里。

## 运行

```bash
# 只列出各阶段和取图请求数，不访问任何服务
python scripts/pipeline/run_site_pipeline.py --name 7828_20261003 --node-id 7828 \
  --node-csv ../net2cell_utdf/build/network/macronet/node.csv --link-csv ../net2cell_utdf/build/network/macronet/link.csv --plan-only

# 真正取图（计费）并跑完整流程；加 --audit-controls 同时做信号标志审计（也计费）
python scripts/pipeline/run_site_pipeline.py --name 7828_20261003 --node-id 7828 --node-csv ... --link-csv ... --acquire --audit-controls
```

已有输入的路口（如 351）用 `--site --base-config --exit-views` 代替 `--node-id`。已完成的阶段自动跳过；`--cache-only` 禁止一切新请求和模型调用。

计费请求必须显式允许：没有 `--acquire` 时，流程打印取图预算后停止。四岔路口典型请求：卫星图 1 张，街景元数据 24 次（不计费，含备选位置最多 72 次），街景图片最多 40 张（每个进口近/中/远前向 + 近处回望，每个出口近/中/远各向外、回望一张）。

## 取图（`fusion/lane_acquisition.py`，`scripts/pipeline/acquire_site_imagery.py`）

- 卫星图按节点中心点和缩放级别请求（默认 zoom 19，1280×1280@2x，约 0.062 m/像素，宽约 160 m）。视口由 Web Mercator 瓦片公式直接算出，不再需要 351 那样用多张不同范围的图做配准。
- 进口、出口的名称、行驶方向和所属道路臂（arm）与描绘阶段的裁剪框来自同一份路网计算（`autoloop/frames.py`），所以各阶段的断面名称一致。四个方位名冲突时改用八方位名（如 NEB），仍冲突才用 link 编号。道路臂按 link 离开路口的方向分组，分隔道路的两条单向 link 归为同一臂。
- 每个拍摄位置先查街景元数据，再检查：在该进口/出口一侧、距中心落在该档范围内、没有偏离道路、与其他档不是同一全景且相距至少 10 m。不合格时依次试 ±20% 的备选位置；都不合格就记为缺失（写进 `gsv_sampling.missing`），不拿别的位置顶替。
- 输出：`site.json`（描绘阶段配置）、`base_config.json`（分类阶段的街景来源和档位）、`exit_views.json`（出口复核和图集）、`acquisition.json`（每次请求、吸附和拒绝原因）、`plan.json`。

## 进口结构与转向（`hybrid/legs.py`）

分类阶段不再假定“东南西北四个进口”。能量的由几何决定，需要判断的交给模型：

- 几何决定：每个断面的行驶方向、所属道路臂、宽度测量轴、街景点是否在进口上游、出口断面对应的回望视图。
- 转向候选：按进口与各出口的方向差给出候选。直行 45° 以内，左/右转到 135°，同一道路臂上的出口是掉头。方向差落在边界附近 20° 以内时同时给出两种候选。
- 模型判断：几何能唯一配对时（普通十字、T 形），提示与原来一样，例如 T 形主干进口只列左转、右转、掉头。斜交或 Y 形路口里，几何无法唯一确定转向的出口，模型看图从候选里选择并说明理由；校验只要求所选转向属于候选，且每个出口一个决定。
- 普通十字路口的提示逐字不变：351 的分类阶段从缓存完整重放，0 次新调用，16 个 movement 决定完全相同。

## 图集（`fusion/bundle.py`）

- 卫星视口取自配置：带 `georeference.kind = viewport` 的图直接用；没有视口的旧图（351）沿用同目录多尺度配准，目录和文件名从配置的图片路径推出。
- 街景位姿取自来源记录（新取图都记录了位置、朝向、视场角）；351 的旧街景由瓦片工具裁出、不带位姿，其位姿文件写在 `configs/autoloop/node_351.json` 的 `legacy_gsv_records`。
- 区域编号用节点号，标题用路口名，目标时间窗为最新一期街景及其前 6 个月（351 得到 2025-10—2025-11，与原来一致；2024 年图像仍为历史）。
- 用相同输入重建 351 图集，与原图集只差一句视口说明文字。

## 实际取图中修正的问题（7750，2026-10-03）

- macronet 的 link 常短于 100 m，远档请求点落在 link 末端之外，原来按到 link 折线的距离判定会误判为“偏离道路”。现在沿路网把道路延续到后续 link（选最接近直行的一条），请求点和检查都用延续后的道路。
- Tempe macronet 把双向道路画成同一中心线上的两条有向 link，且 `from_biway` 为 0（ASU 网络为 1）。现在双向道路按几何判断：同一对节点间反向、且几何重合的 link 视为共用中心线。描绘裁剪框、取图请求点和信号取图都用这一判断；351 的裁剪框不受影响。
- 按中心点请求的 7750 卫星图与 351 已配准图对照：位置差平均 0.1 m、最大 0.14 m，视口公式成立。

## 存放位置

- 完整运行目录（中间图片、缓存、日志，约 10 GB）放在 iCloud 外：默认 `~/Downloads/net2cell_runs`（本机“下载”文件夹，不随 iCloud 同步），由 `configs/paths.json` 的 `runs_root` 指定，环境变量 `NET2CELL_RUNS_ROOT` 可覆盖。批量日志在其下的 `batch_logs/`。
- 每个路口跑完后自动导出到项目内的 `results/<名称>/`（随 iCloud 同步，约 10–17 MB/路口）：
  - `imagery/ geometry/ classification/ exits/ controls/ atlas/`：配置、描绘断面、车道与 movement 预测、出口复核、信号审计、图集数据（含 GeoJSON）和报告；
  - `images/`：卫星图和每张街景原图，按断面、档位、朝向命名；
  - `annotated/`：车道标注图（总图、断面拼图、各断面面板）、候选与模型采纳区域总图、各进口 movement 图、描绘裁剪框规划图、街景对齐图（若有）；渲染图存为 JPEG；
  - `answers/<阶段>/vlm/...`：全部模型原始回答，可直接作为 `--reuse-cache-from` 目录，在没有运行目录时重现或续跑而不再调用模型。
- dashboard 是单个文件 `dashboard/intersection_explorer.html`（随 iCloud 同步）；它的分路口构建缓存在运行目录下的 `dashboard_build/`。原始下载图片缓存仍在项目 `cache/`。
- 单独导出：`python scripts/pipeline/export_results.py tempe_7750 ...`。

### 运行中修正的问题

| 问题 | 处理 |
|---|---|
| 一侧边界只在部分站线可见，起草整体失败 | 允许在看不见的站线填 null（至少两站有数），由相邻站线补齐并标为插值 |
| 某进口未描出，但仍有其街景，分类阶段拒绝启动 | 构建配置时去掉没有断面的进口的街景 |
| 模型把备注写成对象、引用整张卫星总览图 | 备注转为文字；未列出的引用单独记录并标记，候选仍须引用至少一个已列出的来源；修复次数 1 → 2 |
| 出口未描出时模型仍报告向它的转向 | 未提供的出口的决定被丢弃并记录；提示中说明哪些出口未能描出 |
| 整块阴影里的裁剪图看不出车道线 | 平均亮度和 90% 分位都很低的裁剪图做对比度拉伸后给模型，并在提示中说明；普通裁剪图不变 |
| 弯曲或带短接段的 link 整体方位与断面方向不符而中止 | 对描绘得到的断面只记录差异，不再中止 |
| 一个进口没有任何描出的出口 | 跳过该进口的 movement，不再回落到四岔默认 |
| 已开始分类后才修好描绘 | `--retrace`：把该路口原有运行目录改名留存，重跑并复用全部缓存 |

### 与 UTDF 的初步比较

按进口 link 精确对应 UTDF 车道布局，最终 136 个可比进口中车道数一致 56 个。补跑前的 130 个进口里：一致 54，模型少一条 53（其中 22 个少的是 UTDF 的专用右转道），少两条及以上 14，多 9。模型偏向少数一条，常见是短的右转渠化段落在描绘断面之外或被并入相邻区域；也有 UTDF 本身过时的情况（例：Mill & 6th 北进口 2025-11 街景只见左转、电车共用直行和自行车道，UTDF 仍记为 L T R）。差异需逐个核对，不能直接当作模型错误。

## 车道数分歧的图像核查（2026-10-03）

对 80 个模型与 UTDF 车道数不一致的进口逐张核查（`scripts/experiments/build_lane_review_sheets.py` 生成对照图：放大的卫星裁剪图 + 中、近两张前向街景；结论在 `results/reviews/lane_count_review.json`，对照图在 `results/reviews/lane_count_sheets/`）。这是助手对同一批图像的目视判断，不是真值。

| 结论 | 数量 |
|---|---:|
| 图像支持 UTDF（模型错） | 43 |
| 图像支持模型（UTDF 过时或有误） | 21 |
| 都不对 | 3 |
| 看不清 | 13 |

模型出错的主要原因：弯道上裁剪框按 link 整体方向放置、与道路斜交（11）；漏掉路缘右转道，常在自行车道外侧（9）；其他漏道（9）；阴影（8）；多条车道并成一个区域（5）；把对向车道、轨道专用带算进来（4）。UTDF 过时的多在 Mill Ave、Apache Blvd 一带（电车、自行车道改造后）。另发现 UTDF 5278（Apache Boulevard）被匹配到 82 m 外的一条住宅小路节点。部分街景相机落在对向车道一侧或道路外（如 973 的中距离街景在公园里）。

据此的改进方向：裁剪框沿道路折线取向（弯道）；审查提示明确检查自行车道外侧的右转道；部分阴影也做局部增强；进口街景按行驶侧筛选；核对 UTDF→节点匹配距离过大的路口。

UTDF 进口匹配规则统一后（见下节），973 EB、4454 SB 不再算作分歧，上表其余 78 条仍然有效。

## 车道数自动核查（流程阶段，2026-10-03）

`run_site_pipeline.py --reference-movements ../net2cell_utdf/build/movements/movement_utdf.csv` 在出口复核之后加一个阶段 `scripts/pipeline/check_lane_counts.py`（模块 `fusion/lane_check.py`）；不给参考表就跳过。

- 只检查 VLM 车道数与参考（UTDF）不同的进口，每个进口 1 次模型调用。模型只看无标注的卫星裁剪图（行驶方向朝上）和中、近两张前向街景，不知道 VLM 的结果也不知道 UTDF，自己读出停车线处的车道和箭头；看不清时要求它说明而不是猜。
- 代码把读数和两者比较，给出 utdf / model / neither / unclear 及原因（如 model_missed_right_lane）。结果不改动分类结果。
- 输出：运行目录 `lane_check_<name>/`，导出到 `results/<name>/lane_check/`（results.json、summary.json、模型看到的核查图 `sheets/`）。
- UTDF 进口匹配：按进口 link 匹配；同一 link 上挂了几个 UTDF 进口时取与路网进口同名的那个（`lane_check.reference_lanes`、`reference_name`）。批次汇总、合并 dashboard、自动核查三处共用这一规则。之前汇总和核查把同一 link 上几个 UTDF 进口的车道合并计算，dashboard 则取最后一个，三处不一致。

ASU 48 个路口：共 80 次模型调用（规则统一前），统一后从缓存重新判定，没有新调用；检查 78 个进口，结论为 UTDF 对 19、模型对 25、都不对 13、看不清 21。

与人工核查对比（`scripts/experiments/compare_lane_checks.py` → `results/reviews/lane_check_vs_manual.json`）：

| 人工 \ 自动 | utdf | model | neither | unclear |
|---|---:|---:|---:|---:|
| utdf | 13 | 12 | 7 | 10 |
| model | 4 | 10 | 1 | 5 |
| neither | 0 | 0 | 3 | 0 |
| unclear | 2 | 3 | 2 | 6 |

结论相同 32/78。两边都判为 utdf 或 model 的 39 个进口里一致 23 个（59%）；人工置信度中、高的 25 个里一致 15 个。最大的一类分歧（人工判 UTDF 对、自动判模型对，12 个）是自动读数犯了和分类模型一样的错：漏掉自行车道外侧的右转道、把阴影下的车道并成一条，且多数车道读成 "?"（箭头看不清）却仍给出车道数。核查模型和被检查的模型是同一个、看的是同一张裁剪图，错误相关。因此自动核查目前只适合初筛，不能代替人工核查。

用 cv2 数路面标线的试验（2026-10-03，原型未纳入流程）：在行驶方向朝上的卫星裁剪图上，用 top-hat 提取细亮标线、Hough 找近竖直线段、按主方向摆正后聚成标线，再按间距（2.6–4.9 m 为车道，1.2–2.5 m 为自行车道/缓冲带）数出进口车道。在 VLM 与 UTDF 车道数一致的 58 个进口上只对了 9 个，在人工判过的 40 个分歧进口上对了 11 个。失败原因：裁剪图里同时有对向车道，这个分辨率下分不清中央双黄线，常把对向车道也数进来；停车线位置不固定，条带有时落在人行横道和路口内部；整块阴影下检测不到标线；排队车辆遮住虚线；弯道斜交。这些恰好是有争议进口的典型情况，所以不采用。

`movement_utdf.csv` 里有几处 UTDF→路网匹配看起来有误（net2cell_utdf 的问题，这里只如实显示）：7905 NB（UTDF NB 没有 link）；7865（UTDF EB 挂在路网 SB 的 link 15689 上，UTDF SB 没有 link，而 UTDF SB 的 L、R 才与该 link 上看到的一致）；5877（UTDF EB、SB 都挂在 link 10931 上，路网 SB 没有 UTDF）；7897（UTDF NW 挂在路网 NB 的 link 上，路网 NWB 没有 UTDF）。另有 7913、5128、973、7687、4454、7900 的一条 link 上各挂两个 UTDF 进口，可能是斜交进口合并，也可能是匹配错误，未逐一核实。

## 描绘窗口定位、阴影和右转规则（2026-10-03 试跑，2026-10-04 全部 46 个路口重跑完成）

问题：描绘窗口原来完全由路网推算——起点 = 横向道路半宽（网络车道数 × 3.6 m）+ 5 m，方向 = link 折线方向。所以很多进口的框不是从停车线开始（7880 SB 起点在停车线上游约 12 m，漏掉停车线处的箭头）；弯道和路段合并处的 link 带斜向连接段，框与道路斜交（5128 达 30° 以上）。卫星图本身与路网坐标的偏差肉眼看约 1–2 m，不是主因；dashboard 全屏地图把 VLM 车道叠在 Esri 卫星图上也对得上。

- 定位（`autoloop/anchor.py`，描绘版本 autoloop-geometry-4）：每个断面先给模型一条长 65 m、宽 ≥40 m、沿离开路口 25–55 m 处道路方向摆正的探测条带（带 x/y 标尺、淡网格、路网中心十字和路网中心线），让它报出停车线（出口为人行横道下游边缘）的位置，以及目标车行道在停车线处和上游约 25 m 处的左右边界。代码据此把描绘窗口放在停车线后 1 m 起、沿车行道自身方向 28 m 长、按实测宽度加 7 m 边距；看不到停车线或置信度低时只按读数摆正方向（见下文试跑）。每断面 1 次调用，计入描绘预算之外。规划图（`plan.png` / 导出的 `tracing_plan.jpg`）同时画出路网窗口（细虚线）和定位后的窗口，粉色圈是停车线中点。
- 路缘右转道：描绘草稿和审查提示都明确写出“右边界是路缘本身，停车线附近常有一条右转道夹在自行车道和路缘之间，属于车行道”。
- 阴影：整片阴影仍整体拉伸；局部阴影（平滑后暗于日照路面 72% 的面积 ≥20%）按照度比例提亮阴影部分，作为第二张图与原图并排给模型（深色车辆也会被提亮，所以不替换原图）。291 个断面中约 147 个会附上这张图。

## GSV 的利用和与卫星图的对齐（2026-10-04 试跑，2026-10-05 全部 46 个路口重跑完成）

发现的问题：
- GSV 没有被用来数车道。分类阶段的街景提示要求模型“不要给出完整车道数”，只记零散观察；车道数完全来自卫星描绘。例：Apache Blvd（7820）NEB 近景街景里模型已经看到“灰车所在车道左侧有车道线，左边还有一条有白车的车道”，即 2 条，但卫星只描出 1 条，最终就是 1 条。
- 对齐：街景位置取自元数据经纬度，与卫星图同一坐标系。把卫星描绘的车道按相机位姿（2.5 m 高、平地）投影到街景上看，近景基本落在对应车道上，偏差约一条车道以内，弯道上更大（7820 NEB 中景）。已有的位姿拟合模块（`autoloop/gsv_projection.py`，每张街景 2–3 次调用）只在 351 上跑过；更重要的是，流程从未用这种对齐去检查或补充卫星描绘。
- Rural & 6th（7930）：节点本身对，但 macronet 节点在实际路口中心以南约 18 m，几乎压在 NB 停车线上。定位条带从节点向外，所以 in_NB / out_SB 的条带里看不到停车线（只摆正方向，框起点比停车线远约 17 m），out_NB 把南侧人行横道当成了出口起点，框落在路口中央。全部 46 个路口里有 28 个断面的条带中“看不到线”，另有 29 个进口看到了停车线但置信度低被弃用。

改动（描绘版本 autoloop-geometry-6，分类版本 hybrid-pilot-v8-street-view-counts）：
1. 定位条带从节点往路口另一侧多延伸 25 m，提示说明路网路口中心可能偏 20 m 以上、请先找出路口本身；出口起点必须在路口区域外侧。每个路口先读完所有断面，再按道路臂统一起点（`anchor.harmonise`）：同一臂的进口停车线和出口起点在同一人行横道，相差超过 8 m 时以置信度高者为准（相同时以进口停车线为准）；一方读不准时借用另一方（from_arm_partner）；两方都低置信但一致时采用（agreed_low_confidence）。
2. 描绘进口时把最近的前向街景（近景，无则中景）作为面板 S 给模型（`autoloop/street_panel.py`）：卫星裁剪图上标出相机 C 和视野；审查轮把当前边界 e# 按相机位姿投影到街景上，模型据此发现“街景里有车道但没有条带”或“条带落在路缘外/对向车道”。
3. 分类（usage）阶段要求模型数出每张前向街景中本方向的机动车道数，并指出与候选区域不匹配之处，输出结构化 `street_view_counts`；dashboard 每个进口显示 “GSV near 2 · mid 2”，与描绘车道数不同的标出。

## 指定年份取图与并行请求（2026-10-10）

起因：剑桥 Broadway & Ames Street 示例路口 2023 年起在施工，需要施工前的图。

**取图策略**（`--acquisition-policy`，示例 `configs/acquisition/cambridge_pre_construction.json`）
- `satellite.source: "xyz_tiles"`：卫星图改用带日期的正射影像瓦片服务（这次用 MassGIS 2021，15 cm，春季无叶）。
  - 按 Mapbox 请求本来覆盖的 Web Mercator 范围拼图、裁切、重采样，地理配准不变。
  - 拍摄日期和来源写进 `base_config.json` 的 satellite 记录（`date_status: provider_reported`）。
- `capture_before: "YYYY-MM"`：只用这个月之前拍的街景。
  - 官方元数据接口按位置只返回它偏好的那张（通常最新），所以在请求点周围按网格（沿路 ±9 m、横向 ±12 m、间距 3 m、半径 3 m）逐点查询，从中挑出日期合格、位姿检查通过、离请求点最近的那张。
  - 元数据查询不计费，但次数多，`max_metadata_requests` 要调大。
- `official_only: true`：只用谷歌自己拍的全景（版权为 “© Google”）。
  - 小半径查询会碰到第三方上传的全景，包括室内大堂和人行道上拍的，`source=outdoor` 也挡不住。
- `fallback_earliest: true`：某位置没有截止日期前的全景时，改用附近找到的最早一张，并标 `date_fallback`；不开时记为缺失，不会用别的年份顶替。
- 网格查询有盲区：同一位置后来又拍过的话，接口在每个点都只回最新那张，较早的全景就查不到（剑桥 Broadway 东段 140 次查询全是 2026-06，而谷歌地图时光机里还有 2020-11、2018-07 等）。
  - `pinned_panoramas`：按 “断面/位置”（如 `out_EB/near`）直接指定全景 ID。ID 在谷歌地图时光机里选（网址中 `!1s` 后面那段），程序用官方元数据按 ID 查日期和位置，照常做位姿检查，不合格就报错停下，不会悄悄换成别的；采用的相机记 `pinned`。
- `same_carriageway: true`：分隔道路（两个方向是两条分开的 link）上，离本方向 link 超过 6 m 的全景记 `opposite_carriageway` 不用。隔着中央分隔带基本看不清本方向车道；剑桥第一次运行的 out_EB 就误用了对向 WB 车道上的 in_WB 全景。默认关闭，不改变其他路口的结果。
- 路网可以用 Overpass 的历史查询（`[date:"2021-05-01T00:00:00Z"]`）取当年的 OSM，再用 osm2gmns 生成，见 `data/cambridge_kendall_2021/README.md`。

**信号标志审计**（`run_site_pipeline.py --control-policy`）：`preferred_date_window` 加上 `date_search`，在请求点周围找窗口内的全景；找不到时照旧退回其他年份并标 `date_fallback`。
- `known_panoramas`：按截面（如 `in_EB`）列出时光机里找到的全景 ID，日期搜索时加进候选，和查到的全景一起按位置、站点误差和日期窗口挑选；初始取景和追加取景都用。必须同时设 `preferred_date_window` 和 `date_search`。
- `date_fallback: false`：某个取景点找不到窗口内的全景时就空着，不退回其他年份（默认 `true`，照旧退回并标 `date_fallback`）。剑桥改造前的运行关掉了它，免得施工期的标志混进读数。

**目标时段**：出口复核的提示词和 atlas 的时间关系（`historical` / `target_window` / `later`）都按本次运行的目标时段判断，不再写死 2025-10 至 2025-11。目标时段取配置里的 `target_window`，没有时取最新一批街景所在的月份段（`fusion/bundle.py` 的 `target_window`）。卫星图的拍摄日期和说明（`capture_date`、`date_note`）也写进分类和出口复核的图像清单，模型不再被告知“卫星日期未知”。

**出口的最终读法**：出口复核（`exits`）用该出口自己的街景重新判断各区域，结果取代分类阶段对出口的读法。atlas 一直这样合并；现在标注图（`draw_lane_labels.py --exits`）和看板也用同一份结果（`fusion/downstream.py` 的 `with_exit_audits`），三处不再各说各的。

**并行请求**（环境变量 `NET2CELL_PARALLEL_REQUESTS`，默认 1）
- 以下请求彼此独立，可以同时发出，结果仍按原顺序合并：
  - 描线：各断面的停车线定位、各断面的描画和审查循环。
  - 分类：各张街景的读取、各断面的表面分类、各进口的车道用途和转向。
- 代价：调用上限是在每个请求发出前检查的，几个请求同时在途时，实际调用可能超出上限，超出的数目最多为同时在途的请求数减一。
- 适合由多个作答者并行处理请求的后端；用 CreateAI 时注意每分钟 token 限额。
