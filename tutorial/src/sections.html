How to use this tutorial

PAVE is a harness around a vision-language model. The model makes the judgements; the code measures, checks and writes the result into the road network. It has four parts:

PartWhat it does
PPerceiveRenders what the model looks at: rotated satellite crops with rulers and stations, street views with known camera poses, traced lanes projected into those views.
AAnchorTies every answer to something checkable: pixel coordinates on the image, lane IDs on a network section, network link and node IDs.
VVerifyChecks each answer. A failed check goes back to the model with the reason; a measured issue sends a trace back; a second, independent reading decides whether a lane may be dropped.
EEditWrites the answers that pass into lane and movement tables tied to the network, or into the redesigned network.

The tutorial uses the two examples that ship with the repository:

  • Read: the signalised T-junction of Broadway & Ames Street in Cambridge, Massachusetts (network node 95). One run calls the model 9 times, and every one of those calls is shown below.
  • Edit: the SR 347 / I-10 interchange in Arizona, rebuilt from a conventional diamond into a diverging diamond (DDI). One model call, plus a deliberately wrong answer that shows the checks and the repair request.
These prompts and images are the real ones. The Read calls are the run in read/examples/broadway_ames_2021/run/: for each call, the image and the prompt are the ones the run sent and saved, and the answer is the one it got. The example replays from these answers with no model request, and the replay sends the same prompts and images byte for byte. The Edit prompt was regenerated offline by the code and matches the prompt saved in the repository word for word.

This is the single-file edition. The text, every prompt and output, the images and the tools are all inside this one HTML file, so it opens offline and can be passed on as it is. To keep it small, the images are reduced copies (model inputs at most 2000 px on the long edge); the prompts and outputs are complete. A call rerun from these images still works, because the prompts read positions from rulers drawn on the image or as 0–1 fractions, but its request signature will not match the original run.

The call viewer

Every step that calls the model has a viewer. The buttons at the top switch between the calls of that step (different arms or approaches). Below them are the input image (click it for full resolution), the prompt sent to the model (the grey part is the system prompt), the model output, and a command that reruns that one call. Buttons with a dashed border are repair calls: the previous answer failed a structural check, so the code appended the error to the prompt and asked again.

The model only ever answers in JSON. The pictures come from PAVE's code: below each answer, What PAVE makes from this answer shows what the code drew or built from it, which is usually the input of a later call (a trace becomes the lane outlines of the lane-use sheet). Some answers produce no picture and go on as text into a later prompt; the viewer says so.

Model output is a prediction, not reference data.

What is in this folder

  • calls/read/<stage>/ and calls/edit/…: one folder per call, with the original image, system.txt, prompt.txt, the saved answer answer.json and call.json. That is everything needed to rerun any single step.
  • tools/: a single-call tool, a local gateway and a file queue for agent workers, used in the API and agent sections below.
  • images/: reduced copies of the images for this page.

Setup

To read the prompts and outputs you need nothing but this page. To call a model yourself or run a pipeline, set up the following.

1. The pave code

Skip this if you already have it locally. Otherwise:

git clone https://github.com/yajunliu99/pave.git "$PAVE"

2. Python

Read needs Python 3.12 or newer; Edit needs 3.10 or newer. One virtual environment can hold everything:

python3 -m venv ~/.venvs/pave
source ~/.venvs/pave/bin/activate
pip install -r "$PAVE/read/requirements.txt"    # Pillow, NumPy, Requests, OpenCV
pip install -e "$PAVE/edit"

The tutorial's tools/ use only the standard library, plus Pillow (already installed for Read) to read image sizes.

3. Checks that cost nothing

cd "$PAVE/read" && python -m unittest discover -s tests
cd "$PAVE/edit" && python -m pave_edit      # replays the saved answer and builds the DDI, no network access

The Read example also replays from its saved answers, with no model request and no network access:

cd "$PAVE/read"
PAVE_VLM_BACKEND=bridge PAVE_BRIDGE_MODEL=claude-opus-5-5 PAVE_BRIDGE_PROVIDER=claude_code_subagent \
python scripts/pipeline/run_read.py --imagery examples/broadway_ames_2021/imagery --output runs/example_replay \
  --reuse-cache-from examples/broadway_ames_2021/run --cache-only

The three variables name the model and the agent that answered the saved run, so that its answers are found in the cache; nothing is sent anywhere.

API setup

The two pipelines use three kinds of service. For Edit alone, or for single-step practice with this tutorial's calls/, you only need a model.

ServiceSetting (in .env)Used byNotes
Mapbox Static ImagesMAPBOX_TOKENRead step 2 satellite image; Edit when fetching imagery for a new siteNot needed with key-free XYZ tiles, such as the MassGIS 2021 orthophoto in the example.
Google Street View Static APIGSV_API_KEYRead step 2Metadata requests are free; image requests are billed. Required to fetch imagery for a new site.
Vision-language modelOPENAI_API_KEY, OPENAI_MODEL, OPENAI_BASE_URLRead steps 3–7; Edit step 3Any OpenAI-compatible Chat Completions API (below). With no API at all, coding agents can answer (next section).

All of them go into one file: copy .env.example at the pave root to .env (cp "$PAVE/.env.example" "$PAVE/.env"). Read and Edit both read it; a variable set in the environment takes precedence over the file. .env is in .gitignore. Don't send it to anyone or paste it into a chat.

Mapbox token

  1. Sign up and log in at account.mapbox.com.
  2. On the Tokens page, copy the default public token (it starts with pk.). It can call the Static Images API.
  3. Put it in .env: MAPBOX_TOKEN=pk.…

For orthophotos of a particular period, set satellite.source to xyz_tiles with a tile URL in the acquisition policy, as the example does (see read/configs/acquisition/cambridge_pre_construction.json). Mapbox is then not needed.

Google Street View key

  1. In the Google Cloud Console, create a project and turn on billing for it.
  2. APIs & Services → Library: search for Street View Static API and enable it.
  3. APIs & Services → Credentials → Create credentials → API key.
  4. Edit the key: under API restrictions, allow only the Street View Static API. Add an IP restriction if your outgoing address is fixed.
  5. Put it in .env: GSV_API_KEY=…

Use --plan-only first to see the request budget without any network access or cost (step 2). For this example: 1 satellite image, about 18 metadata requests (at most 54), at most 30 street-view images.

The Street View metadata service returns only the latest panorama at a location. The example needs the November 2020 panoramas, from before the junction was rebuilt, and newer 2024 and 2026 captures hide them. The acquisition policy therefore names one panorama ID per position in pinned_panoramas, looked up in Google Maps' historical Street View. You need the same for any other period.

The model: any OpenAI-compatible API

Read and Edit send every request through one client, read/pave_read/vision_client.py (Edit keeps an identical copy): one POST <base URL>/chat/completions with the system prompt, the prompt and one image as a base64 data URL at its original pixel size, asking for a JSON object. Any server that speaks this protocol works: OpenAI itself, a provider's OpenAI-compatible mode, OpenRouter, or a model you host with vLLM or Ollama.

1. Fill in .env

OPENAI_API_KEY=...
OPENAI_MODEL=...         # a model that accepts images, as the API names it
OPENAI_BASE_URL=...      # only for a server other than OpenAI's (default https://api.openai.com/v1)

The model's name is recorded with every answer and is part of every cache key. A name like vendor/model-name (usual on gateways and OpenRouter) is recorded as model model-name from provider vendor; a plain name is recorded with the API's host as the provider. One model's answers are never reused for another, so different models can share a run folder.

What the model and the server must handle: image input; a JSON answer when asked with response_format: json_object; the parameters max_completion_tokens and temperature: 0, which Read sends on every request; and sheets of up to about 4,300 × 1,900 pixels (the trace sheets). Read allows up to 16,384 output tokens for lane use and 12,288 for a trace. If your server rejects one of these parameters, see Troubleshooting.

2. Test one call

Before a whole junction, send one of the tutorial's saved calls with the same settings:

cd "$TUT"
PAVE_ENV_FILE="$PAVE/.env" python tools/call_vlm.py --call calls/read/read_EB --backend openai

PAVE_ENV_FILE lets the tool read pave's .env. The answer is saved as calls/read/read_EB/my_answer.openai.json, next to the saved answer.json for comparison. An HTTP error here (a wrong key, a model without image input, an unknown parameter) is cheaper to find on one call than in the middle of a junction.

3. Run a junction

Fetch the imagery once, then read the junction:

cd "$PAVE/read"
python scripts/pipeline/acquire_site_imagery.py --node-id 95 \
  --node-csv examples/broadway_ames_2021/network/node.csv \
  --link-csv examples/broadway_ames_2021/network/link.csv \
  --policy configs/acquisition/cambridge_pre_construction.json \
  --output runs/imagery_broadway_95
python scripts/pipeline/run_read.py --imagery runs/imagery_broadway_95 --output runs/read_broadway_95

The example's imagery is already in the repository, so to read it with your own model you can skip the first command and pass --imagery examples/broadway_ames_2021/imagery. Each answer is cached in the run folder as vlm/<step>/<signature>.raw.json. The signature covers the image, the prompt, the system prompt, the model and the protocol, so a rerun never pays twice for the same request. Run folders go under runs/ in read/; PAVE_RUNS_ROOT moves them.

4. Edit

cd "$PAVE/edit"
python -m pave_edit --backend openai --hide-names

Edit reads the same .env (in edit/ or at the pave root); --env-file names another file and --model another model. Answers are cached in edit/cache/openai/.

Know the cost before you start

  • Read makes about 12–20 model calls at a four-arm junction: a trace of each arm, a blind reading and a lane-use call for each approach, and further calls only where a check asks for them. The example, a T-junction, took 9.
  • Edit makes 1 call per run (plus at most 1 repair if the first answer fails).
  • --plan-only shows the imagery budget; --max-calls caps a Read run's model calls (40 by default); --cache-only forbids any new request and only replays the cache.

No API: let agents answer

A coding agent such as Codex or Claude Code can open an image file on disk, crop and enlarge parts of it with Python, and write JSON, so it can answer these prompts in place of an API. Read has a file queue for this built in: each request waits in the queue until an agent answers it.

It is slow and uses many tokens: expect several minutes and tens of thousands of tokens per request, because the agent crops many details to inspect them. In the example run the traces took about 10–20 minutes each and the other calls 1–7 minutes. Use it for learning, for spot checks and for second opinions; use an API for batches.

The examples below are written for Codex in the ChatGPT desktop app, where you type prompts and Codex runs the commands itself; any agent that can run commands and start subagents works the same way. In the app, create a local project for the tutorial folder, attach the pave folder to it (Edit project → Add folder), and switch the chat composer to Work so Codex can use files and run commands. Codex starts subagents only when you ask for them explicitly ("spawn …", "one agent per …"), and each subagent's thread is shown in the app.

1. One step (simplest)

In a chat in the project, send the following (change the call folder to the one you want to rerun):

Spawn one subagent for this task and wait for it, then show me its final JSON as it is.
Task for the subagent:
Read calls/read/trace_SE/call.json, then read the system.txt and prompt.txt files it names
and inspect the image file it names. Where a detail is hard to see (lane lines, arrows, sign text,
ruler ticks), crop and enlarge that region with Python/PIL and inspect the crop. Give coordinates
in the units the prompt asks for, and add the crop offset back to readings taken on a crop.
Answer from the prompt and this image only: do not open answer.json or any other file.
Write exactly one JSON object, as the prompt asks, to calls/read/trace_SE/my_answer.codex.json.

"Do not open answer.json" matters: it is the saved answer, and an answer written after reading it is no longer an independent reading. Afterwards you can ask Codex to compare my_answer.codex.json with answer.json field by field.

2. A whole junction (Read's queue)

With PAVE_VLM_BACKEND=bridge, Read writes each request to a queue folder instead of calling an API, and waits for its answer. The agents answer through read/scripts/pipeline/vlm_bridge.py, following the worker instructions in read/docs/agent_queue.md. Start one fresh subagent per request: no subagent then sees more than one request, so no answer depends on an earlier one.

Prompt 1: start the pipeline

Start one long-running background process and keep it running; tell me if it stops.
In the pave folder, from pave/read, with these environment variables (for this run only):
  PAVE_VLM_BACKEND=bridge
  PAVE_VLM_BRIDGE_DIR=<tutorial folder>/queue
  PAVE_BRIDGE_MODEL=<the model your subagents run>
  PAVE_BRIDGE_PROVIDER=codex_subagent
  PAVE_RUNS_ROOT=<tutorial folder>/runs
  PAVE_PARALLEL_REQUESTS=3
run:
  python3 scripts/pipeline/run_read.py --imagery examples/broadway_ames_2021/imagery \
    --output <tutorial folder>/runs/read_broadway_95

The first two variables send Read's requests to the queue in the tutorial folder, where Codex may write. The next two are recorded with every answer, so these answers never mix with an API model's. PAVE_PARALLEL_REQUESTS=3 lets a step keep three independent requests open at once (the three traces, the three readings, the three lane-use calls), so three subagents can work side by side.

Prompt 2: answer what is waiting

Check the queue: PAVE_VLM_BRIDGE_DIR=<tutorial folder>/queue python3 scripts/pipeline/vlm_bridge.py status
(from pave/read). For each pending request, spawn one subagent with this task, with its own NAME
(w1_001, w1_002, ...) and QUEUE = <tutorial folder>/queue:
  "You are a one-shot vision worker. NAME = <name>, QUEUE = <queue>. Read the section
   'Worker instructions' in pave/read/docs/agent_queue.md and follow it exactly."
Wait for them, then check the queue again and repeat while the pipeline is still running.
Report the request ids that were answered and whether the pipeline finished.

Most requests depend on earlier answers (lane use needs the traces), so new requests appear only after earlier ones are answered; that is why Prompt 2 checks again. If a subagent stops without answering, its request stays claimed: put it back with vlm_bridge.py release --older-than-min 30. If the pipeline stops (for example when the app is closed), send Prompt 1 again: answered requests are taken from the cache, and requests still in the queue are waited for, not asked again.

To try an agent on a single saved call without the pipeline, python3 tools/call_vlm.py --call calls/read/read_EB --backend queue puts it in the tutorial's own queue; tools/SUBAGENT_WORKER.md tells a subagent how to answer it.

3. Edit (built into pave)

Edit already supports a chat model as the proposer. Send this in a chat in the project:

In the pave folder, from pave/edit:
1. Run: python3 -m pave_edit --prepare-only --hide-names --out out/session
   It writes out/session/ai_input.png and out/session/ai_prompt.txt.
2. Spawn one subagent. It reads out/session/ai_prompt.txt in full, inspects out/session/ai_input.png
   (cropping and enlarging where needed), and writes exactly the one JSON object the prompt asks for
   to out/session/answer.json. It must not open anything under scenarios/ (saved answers are there).
3. When it is done, run:
   python3 -m pave_edit --backend session --proposal out/session/answer.json --hide-names

If the checks reject the answer, pave writes out/session/repair_prompt.txt (the original prompt, the rejected answer and the defects). Ask Codex to give that file to a subagent as its new prompt, then run step 3 again with the corrected answer.

Rules for agents

  • Independent: only the prompt and the image (and its own crops of it). No run folders, caches, earlier answers, reference data, code or web.
  • No guessing: what cannot be seen goes into the fields the prompt provides (confidence, limitations, notes).
  • Units: the ruler units where the prompt asks for coordinates on the image. Where it asks for 0–1 boxes (such as bbox_xyxy of a detail request), give fractions of the named panel, not of the whole sheet.
  • One request each: a subagent that read an approach blind should not also answer its lane use; with one fresh subagent per request this holds by itself.

Read overview: Broadway & Ames Street

A signalised T-junction in Kendall Square, Cambridge. Broadway runs east–west with a median near the junction and bicycle lanes in both directions; Ames Street joins from the south. The junction was rebuilt around 2022–2023, so this run reads it from imagery taken before that work: the MassGIS spring 2021 orthophoto (15 cm, leaf-off) and Street View from November 2020. The network is OpenStreetMap as of 1 May 2021, converted to GMNS; the junction is node 95.

Two readings, kept apart. The trace (step 3) and the blind reading (step 4) look at the same approach without seeing each other's answer. The command that runs this junction is under API setup → The model.

P

1 Network node and arms

no model calls
INPUTnode 95 and the links that meet it (GMNS node.csv, link.csv)
THE CODEgroups the links into arms and cuts a window along each arm
OUTPUT3 arms: SE (Broadway east), SW (Ames Street), NW (Broadway west)

The links that end at the node are the approaches; the links that start there are the exits. An approach and an exit that run along the same road form an arm. Here every arm has one of each: arm SE holds approach WB and exit EB, arm SW approach NB and exit SB, arm NW approach EB and exit WB.

For each arm the code cuts a window from the satellite image along the link's heading, rotated so that traffic entering the junction on that arm drives up and the junction lies at the top. The window's size and placement come from the link geometry only: no lane count from the network is used, so a wrong count in the network cannot steer the reading.

Troubleshooting

  
"OPENAI_API_KEY not found" or "no model given"

  
pave did not find its settings. They belong in .env at the pave root (Read also reads read/.env, Edit edit/.env), or in the environment of the run. With Read's agent queue (PAVE_VLM_BACKEND=bridge) no API settings are needed.

  
"requested model …, the response came from …"

  
The server answered with a different model than OPENAI_MODEL; pave accepts only the same name or a dated variant of it (name-2026-…). Set OPENAI_MODEL to the name the server reports.

  
"model mismatch: requested …, received …"

  
A cached answer recorded under another model is being reused, for example with --reuse-cache-from a run made with a different model. Use the same model (for the example: the three variables under Setup), or a fresh run folder.

  
The server rejects temperature, max_completion_tokens or response_format

  
pave's client always sends them. Put the tutorial's gateway in between: fill in your API's OPENAI_* in tools/.env, add OPENAI_LEGACY_MAX_TOKENS=1 and/or OPENAI_JSON_MODE=0 as needed, start python tools/pave_gateway.py --backend openai, and run pave with OPENAI_BASE_URL=http://127.0.0.1:8765/v1, OPENAI_API_KEY=local and OPENAI_MODEL set to your model's name. The gateway sends no temperature and adapts the other two.

  
"VLM API call budget exhausted"

  
The run's --max-calls (40 by default) is used up. It is a guard against runaway spending; check whether something is retrying over and over.

  
Timeout: "timed out" after 150 seconds

  
Read waits 150 seconds per API request, with one retry. For a slow API, set PAVE_VLM_TIMEOUT_S (seconds) in the run's environment. A request in the agent queue waits up to 4 hours (PAVE_BRIDGE_TIMEOUT_S).

  
Structural check failures

  
Read appends the error to the prompt and asks again automatically, at most 2 times (these are the dashed buttons in the viewers); if it still fails, the step stops with an error. Edit allows 1 repair (--max-repairs).

  
Replay without spending anything

  
Add --cache-only to Read: any request without a cached answer fails instead of being sent. Edit's default mock backend is a replay.

  
A different model gives different results than this tutorial

  
That is expected. The outputs here are one model's prediction on one run, not the right answer. Compare whether the structure and the evidence hold up, not whether the words match.

  
Nobody answers the queued requests

  
Check the counts with python scripts/pipeline/vlm_bridge.py status (from read/, with PAVE_VLM_BRIDGE_DIR set to the queue). Requests that stay claimed for a long time mean the agent stopped: put them back with release --older-than-min 30 and start an agent again. On a rerun of the pipeline, answered requests are taken from the cache and unanswered ones keep waiting in the queue.
